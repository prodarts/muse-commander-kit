# フル配線ガイド（AI実行用手順書）

このドキュメントは、導入する人のAI（Muse など）が順に実行して構築するための手順書です。
AIが自分でできる手順と、本人でないとできない手順を分けてあります。****と付いた手順は、AIが案内し、本人が実行して結果をAIに伝えます。鍵やパスワードをAIに渡してはいけません。

新しいPCを買って同じ環境を作り直す場合も、この手順書がそのまま使えます。資産（台帳・手順・テンプレート）は共有ドライブと GitHub から戻し、鍵とログインは新しいPCで作り直すのが原則です。

（最終確認：2026年11月。CLI のコマンドやオプションは版で変わるので、実行時に公式ドキュメントで確認すること）

## フェーズ0：導入範囲を決める

README の構成パターン A〜D のどれにするか決める。
- A（Muse 単独）→ フェーズ1だけ。完了条件はフェーズ1の検証
- B（＋Codex）／C（＋Claude Code）／D（両方）→ フェーズ1〜4

あわせて、司令塔のAIに「シェルや SSH でコマンドを実行する手段」があるか確認する。無ければ B〜D は成立しないので、A で止める（その場合は、指示書と報告書を本人が運ぶ形も選べる）。

## フェーズ1：ドキュメント運用を作る

1. `templates/` の3ファイルを、本人の作業場所にコピーする
- SOUL.template.md → SOUL.md（判断ルール）
- AGENTS.template.md → AGENTS.md（作業の進め方）
- BRIEF.template.md → 指示書の雛形として保管
- 既に同名ファイルがある場合は上書きせず、差分を見て統合する
- 注意：Codex は作業フォルダの `AGENTS.md` を自分への指示として自動で読む。司令塔用と部下用で内容がぶつかる場合は、置き場所を分ける
2. SOUL.md と AGENTS.md の中身を、本人の仕事に合わせて最小限で埋める。最初はスカスカでよい。完璧を狙わない
3. 裁定台帳の正本を、共有ドライブに作る（筆者運用は Google Drive の共有フォルダにドキュメント1つ）
- 先頭行に「最終更新：日付」を置く
- 項目の形は `docs/ruling-ledger.md` の通り（ID／本文／範囲／条件・例外／由来／見直し日／状態）
- **正本を更新するのは司令塔だけ**（本人の承認後）。部下AIには、その仕事に必要なルールを指示書に添えて渡す。部下が正本を直接書き換えない
- 司令塔は、仕事を始めるたびに正本の現行ルールを読み直す。メモリの要約と食い違ったら正本が勝つ
- 正本が読めないときは、古い要約で進めず、止まって本人に知らせる
4. 本人に宣言する：「あなたが指揮、わたしが司令塔。決めたことは台帳に貯めて二度聞きません」
5. 検証：本人に小さな判断を1つしてもらい、ルール案→承認→台帳に1行入る、まで回ればフェーズ1完了（パターン A はここで構築完了）

## フェーズ2：実行機を配線する（パターン B〜D のみ）

前提：実行機（自宅PC）は常時電源ON。筆者の検証環境は Mac（macOS）。Windows／Linux はこの手順では未検証。

鍵の置き場所を先に整理する（混同しやすい所）：
- **SSH の秘密鍵**は、接続元（司令塔が動く側）の安全な場所に置く。公開鍵だけを実行機に登録する
- **Claude Code／Codex の認証（ログイン情報）**は、実行機の中だけに置く。司令塔側には渡さない

手順：
1. 実行機と、司令塔が動く側の両方に Tailscale を入れ、同じアカウントでサインインする
2. macOS の「リモートログイン」を有効にする（システム設定 → 一般 → 共有）。許可するユーザーを絞る
3. 実行機の Tailscale 上のアドレスを確認し、SSH 鍵ペアを用意して公開鍵を実行機に登録する。初回接続ではホスト鍵を目で照合する（検証を無効化して進まない）
- つまずき：PC がスリープすると接続が不安定になる。実行中はスリープさせない設定にする
4. 実行機に部下AIの CLI を入れる（B=Codex、C=Claude Code、D=両方）。それぞれ本人のアカウントで認証する。サブスクリプション認証と API キー課金は別物なので、意図した方で入っているか確認する
- つまずき：SSH 経由の非対話セッションでは、macOS の Keychain が読めず、CLI が「未ログイン」扱いになることがある。その場合は各 CLI の公式手順で長期トークンを発行し、実行機側で使う（司令塔側には渡さない）
- つまずき：SSH 先では PATH が手元と違い、入れたはずの CLI が見つからないことがある。絶対パスで確認する
5. 派遣用の小さなスクリプトを用意する。見本は `templates/dispatch.example.sh`
- 仕事ごとに専用フォルダを作り、指示書・報告書・セッションID・開始／終了時刻・成否をそこに残す
- セッションIDは CLI が返す値から取る（Claude Code は JSON 出力の `session_id`、Codex は `--json` の `thread.started` の `thread_id`。2026年11月時点）

## フェーズ3：派遣の型を固定する

1. 仕事の振り分け基準を AGENTS.md に書く
- 軽い調べ物・要約・件数確認 → 司令塔が自分でやる
- 大きな実装 → Codex に指示書で投げる
- 設計・文章・見た目の制作 → Claude Code に投げる。見た目が要る制作物は絵コンテ（下案）を先に出し、本人が承認してから本制作
- 部下同士は直接やり取りしない。レビューも報告も、全部司令塔を通る
- 3者協議は、本人が言ったときだけ
2. 指示書（BRIEF）の形を固定する：目的／固定する内容／やらないこと／成果物の置き場／報告形式（結論・判断・詰まった所・環境の癖・セッションID）
3. 報告の置き場を、1プロジェクトにつき司令塔とのチャット1スレッドに決める。本人が報告を探し回らない形にする
4. 無人実行の安全を決める
- 初回の検証は読み取り専用の仕事で回す
- 部下が承認の要る操作（送信・投稿・支払い・削除）に当たったら、実行せず「承認待ち」として報告させる
- 接続が切れたら、再派遣の前に実行機側でプロセスが生きているか確認する（二重実行の防止）
- 認証切れは本人に戻す。使用枠の上限に当たったら止めるか、承認済みの代替担当に回す

## フェーズ4：検証（パターン B〜D）

1. 小さな読み取り専用の仕事を1つ選び、指示書→実行→報告書の往復を最後まで回す
2. チェックリスト
- [] 部下AIの報告書が司令塔経由で本人に届いたか
- [] セッションIDが CLI の返した値で記録されたか
- [] その仕事で出た判断が、台帳に1行入ったか
- [] 別セッションで、そのルールが実際に効いたか
- [] Claude／Codex の認証情報が司令塔側に無いか
- [] 承認の要る操作で、部下が止まって報告したか
3. 1つでも欠けたら、その段の手順に戻って直す。全部通れば構築完了

## つまずきどころ（実例）

- クラウド保存のファイルが「未ダウンロード」状態（iCloud の dataless）だと、読み込みで無言で止まることがある。派遣前に使う素材をダウンロード済みにしておく。Google Drive のストリーミング保存でも同じことが起きる
- GUI アプリの自動操作は当てにならない。CLI で完結する仕事から任せる
- 「直前のセッション再開」は並行作業と混ざる。セッションID明示が必須（`docs/session-rule.md`）
- いきなりフル配線にしない。フェーズ1で指揮系統に慣れてから配線する方が、結局速い
